# Known Limitations

> 三层方案的已知局限性。诚实面对限制，才能做出正确的技术选型。

---

## 通用限制（所有层）

### 1. 无法根治 Attention 机制的数学本质

LLM 的注意力漂移源于 Transformer 架构中 Attention 机制的固有特性：
- Softmax 归一化导致注意力在长上下文中被"稀释"
- 位置编码在超长序列中的退化
- KV Cache 积累的数值误差

**所有方案都是"缓解"而非"根治"。**

### 2. 依赖底层模型的基础能力

- 指令遵循能力弱的模型，无论哪一层都难以保持注意力
- 小模型（<7B）在 20+ 轮对话中几乎必然漂移
- 推荐最小模型规格：GPT-4o-mini / Claude Haiku 4.5 级别

### 3. 无法处理对抗性输入

- 用户故意频繁切换话题
- 用户给出自相矛盾的指令
- Prompt Injection 攻击

### 4. 资源消耗与效果的正相关

```
效果 ↑ → Token 消耗 ↑ → 延迟 ↑ → 成本 ↑
```

不存在"既有效又免费"的方案。每加一层，成本增加，效果提升。在两者间权衡。

## L1 Prompt Layer 特定限制

| 限制 | 影响 | 缓解方式 |
|------|------|----------|
| 仅靠文本指令约束，无强制机制 | 模型可能"忘记"自检要求 | 升级到 L2（压缩让约束不沉底） |
| 增加每轮 token 开销（~200–500 tokens/轮） | 长对话成本累积 | 使用精简版 prompt（见 QUICKSTART） |
| 周期性自检可能被模型忽略 | 高负载轮次跳过自检 | 降低自检频率；结合 L3 状态门控强制检查 |
| Prompt 本身成为上下文噪声 | 极长对话中 System Prompt 被稀释 | 升级到 L2 Context Layer |
| 对非英语/非主流语言效果下降 | 中文、日语等的指令遵循弱于英语 | 使用对应语言优化版（system_prompt_zh.md） |

### 效果天花板

- 10 轮以内：效果显著（IFR 提升 20%+）
- 10–30 轮：效果递减
- 30 轮以上：几乎无额外效果（天花板 ~60% IFR）→ **必须升级到 L2**

## L2 Context Layer 特定限制

| 限制 | 影响 | 缓解方式 |
|------|------|----------|
| 压缩可能丢失微妙上下文线索 | 模型失去对细微语义的理解 | 保留最近 3 轮原始对话 |
| 压缩操作本身消耗 token | 每次压缩约 500–1500 tokens | 优化触发时机，不过于频繁 |
| 压缩质量依赖提取 prompt | 差劲 prompt → 关键信息被丢弃 | 使用 state_summary_schema.json 约束结构 |
| 不适合需要精确原文的场景 | 法律、医疗等需要逐字记录 | RAG + 原文引用 |
| 增量压缩可能累积错误 | 错误摘要导致后续偏差放大 | 每 3 次增量后做一次全量重压缩 |
| 摘要器本身也可能漂移 | 这是用 LLM 治理 LLM 的根本矛盾 | 结构化字段 > 自然语言摘要；最近原文兜底 |
| 错误纠正可能被摘要器遗漏 | 用户在第 10 轮纠正了错误，第 15 轮压缩时未捕获 → 第 20 轮错误复现 | `still_valid` 标记 + `confidence: disputed` + 最近原文兜底 |

### 效果天花板

- 50 轮以内效果显著
- 50–100 轮：摘要本身也在变长，需要结合 L3
- 100 轮以上：需要递归压缩（摘要的摘要），复杂度陡增

---

## L3 State Layer 特定限制

| 限制 | 影响 | 缓解方式 |
|------|------|----------|
| 架构复杂度高 | 实现和维护成本大 | 从 L1 → L2 → L3 渐进升级 |
| 状态爆炸风险 | 状态过多导致转移矩阵不可维护 | 控制在 7 个状态以内 |
| Checkpoint 存储成本 | 每次 checkpoint 消耗存储 | 设置 checkpoint 保留策略（保留最近 5 个） |
| 状态定义依赖领域知识 | 需要理解业务才能设计好状态机 | 先用通用状态（RESEARCH / DECISION / VERIFYING）起步 |
| LangGraph 学习曲线 | 团队需要学新框架 | Dify 低代码替代；minimal_example.py 快速上手 |
| 每次状态转换可能引入 LLM 调用 | 延迟和成本上升 | 规则强制切换（绕过 LLM 自判延迟） |
| **L3 不消灭漂移，只限制发散半径** | 模型在 RESEARCH 状态下仍然可能"过度分析"——它在 Allowed 集合内漂移 | 这是设计意图而非 bug。FORBIDDEN 集合越大，状态内自由度越低，但也会让模型过于僵硬 |
| FORBIDDEN 是文本约束，非物理禁止 | 指令遵循能力弱的模型可能突破 FORBIDDEN | 结合 stop_sequences 截断 + 输出后处理过滤 |

### 效果天花板

- 状态机本身不会漂移——但 LLM 节点的输出仍然会
- 复杂状态转移逻辑可能成为新的故障点
- 100 轮以上仍需结合 L2 的压缩策略（三层叠加是最佳实践）

## 已知的技术边界

### Context Window 物理限制

无论哪层方案，都无法突破模型的 context window 物理上限：

| 模型 | Max Context | 不加控制的有效轮次 | L1+L2+L3 可控轮次 |
|------|------------|-------------------|-------------------|
| GPT-4o | 128K | ~30 | ~200 |
| Claude Sonnet 4.6 | 200K | ~50 | ~300 |
| Gemini 2.5 Pro | 1M | ~100 | ~500 |
| 开源 7B (32K) | 32K | ~10 | ~30 |

### "迷失中间"（Lost in the Middle）问题

模型天然倾向于关注上下文的开头和结尾，忽略中间部分。即使 L2 压缩将关键信息注入上下文，如果这些信息恰好处于注入文本的"中间位置"，模型仍可能忽略。

### 评估噪声

- 评审 LLM 本身也可能漂移
- 人工评估成本高，难以大规模进行
- 缺乏行业标准的漂移控制 benchmark

## 不建议使用的场景

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| 法律文书逐字审查 | 压缩丢失原文，状态机不适用 | RAG + 原文引用 |
| 医疗诊断 | 任何信息丢失都可能造成严重后果 | 逐轮全量保留 + 人工审核 |
| 实时客服（<3 轮） | 漂移控制完全不需要 | 简单的 system prompt 即可 |
| 创意写作 | 发散思维可能是预期行为 | 不做漂移控制 |
| 多语言频繁切换 | 压缩和检测 prompt 通常只优化一种语言 | 按语言独立部署各层 |

## 未来改进方向

1. **嵌入级注意力监控**：在 embedding 空间检测注意力分布变化，替代纯文本漂移检测
2. **自适应压缩率**：根据对话复杂度和漂移程度动态调整压缩策略和触发频率
3. **多模态漂移控制**：扩展到视觉-语言模型的注意力漂移
4. **跨会话记忆**：在多个独立会话间保持一致的知识和约束
5. **模型微调**：通过 fine-tuning 让模型原生具备漂移感知和状态边界意识

---

> **核心原则**：没有银弹。三层方案是"围堵"策略——每一层缩小漂移的伤害半径，但不声称消灭漂移。选择适合你场景的层级，理解其边界，在效果和成本间做务实选择。
