# v3 — State Machine 层

> **不是终极解法。** v3 不承诺消除漂移——它只做一件事：**把模型的发散半径限制在单个状态内部。**

---

## 定位：为什么 State Machine 不是银弹

v1（Prompt）、v2（API 参数）、v2.5（压缩）有一个共同的困境：它们在全局空间里对抗漂移。Prompt 说"不要跑题"，但模型在 40 轮后仍然可能从"财报分析"一路偏到"宏观经济理论"再偏到"人生建议"——这是一个**无边界发散**。

v3 换了一个思路：**既然无法阻止发散，那就给发散加上围栏。**

```
无状态控制（v1/v2/v2.5）：
  模型可能从任何话题偏到任何话题
  [分析] → [建议] → [哲学] → [安慰] → [写诗] → ...

有状态控制（v3）：
  模型只能在当前状态的允许行为集合内发散
  RESEARCH 状态：[分析] → [更深的分析] → [换个角度的分析] → [仍然在分析]
                   ↑ 即使漂移，也只是在"分析"这个圈子里打转
```

**核心洞察**：一个在 RESEARCH 状态下过度分析、反复推敲的模型，是一个"笨但安全"的模型。它没有完成任务的效率，但也不会给出不该给的确定性建议。**发散半径被状态边界截断了。**

---

## 状态定义：每个状态都是一组行为约束

### 示例：两个核心状态的 ALLOWED / FORBIDDEN

```
State: RESEARCH
├── Allowed（允许的行为）:
│   ├── 分析数据、事实、趋势
│   ├── 提出假设并验证
│   ├── 列出多种可能性
│   ├── 请求更多信息
│   └── 引用来源和证据
│
├── Forbidden（禁止的行为）:
│   ├── 给出确定性建议或结论
│   ├── 安慰用户、表达同情（不属于分析任务）
│   ├── 哲学扩展、抽象升华
│   ├── 猜测用户意图而不先确认
│   └── 切换到不相关的知识领域
│
└── 转移条件:
    → DECISION: 用户明确要求"给出建议"或"做出选择"
    → CLARIFY:  关键信息缺失，无法继续分析


State: DECISION
├── Allowed（允许的行为）:
│   ├── 给出具体建议并排序
│   ├── 做风险分析和 trade-off 对比
│   ├── 基于已分析的事实做判断
│   └── 指出建议的边界条件和假设
│
├── Forbidden（禁止的行为）:
│   ├── 重新开始大规模分析（回到 RESEARCH 的事）
│   ├── 引入全新的理论框架
│   ├── 回避决策——"这取决于很多因素"
│   └── 推翻之前已确认的事实而不标注
│
└── 转移条件:
    → RESEARCH:  用户说"等一下，先重新看看数据"
    → VERIFYING: 建议已给出，等待确认
```

### 通用状态全集

| 状态 | 一句话定位 | 核心 Allowed | 核心 Forbidden |
|------|-----------|-------------|---------------|
| `INIT` | 解析任务 | 提取约束、识别任务类型 | 执行任务（还没搞清楚呢） |
| `CLARIFY` | 追问补全 | 提问、确认理解 | 猜测、假设补全 |
| `RESEARCH` | 分析探索 | 分析、假设、验证、引用 | 建议、安慰、哲学扩展 |
| `DECISION` | 判断输出 | 建议、排序、风险分析 | 新理论构建、回避决策 |
| `VERIFYING` | 自检收尾 | 逐项核对、补充遗漏 | 引入新任务、重新分析 |
| `COMPLETED` | 交付 | 生成摘要、标记完成 | 继续对话 |
| `DRIFT_RECOVERY` | 紧急恢复 | 声明偏离、回退焦点 | 装作无事发生 |

## 核心机制：每次回复前注入状态专属 Prompt

这是 v3 和 v1 的关键区别。v1 有一个固定的 system prompt，从第一轮到第一百轮都一样。v3 **在每次 LLM 调用前，根据当前状态动态拼接行为约束**。

```python
# 每次回复前的注入逻辑（伪代码）

STATE_PROMPTS = {
    "RESEARCH": """
        ## 当前状态：RESEARCH（分析探索阶段）
        ## 允许的行为
        - 分析数据、事实、趋势
        - 提出假设并验证
        - 列出多种可能性
        - 引用来源和证据
        ## 禁止的行为
        - 给出确定性建议或结论
        - 安慰用户或表达无关的同情
        - 哲学扩展、抽象升华
        - 猜测用户意图而不先确认
        ## 如果用户要求建议
        回复："这需要进入决策阶段。要我现在切换到 DECISION 模式吗？"
        """,

    "DECISION": """
        ## 当前状态：DECISION（决策输出阶段）
        ## 允许的行为
        - 给出具体建议并排序
        - 做风险分析和 trade-off 对比
        - 基于已分析的事实做判断
        ## 禁止的行为
        - 重新开始大规模分析
        - 引入全新的理论框架
        - 回避决策（"这取决于很多因素"）
        ## 如果用户提出新分析需求
        回复："需要先回到 RESEARCH 状态重新分析。要切换吗？"
        """,
}


def build_system_prompt_for_turn(state: str, base_prompt: str) -> str:
    """每次 LLM 调用前，根据当前状态拼接约束"""
    state_prompt = STATE_PROMPTS.get(state, "")
    return f"{base_prompt}\n\n{state_prompt}"
```

### 为什么这能控制漂移

模型在 RESEARCH 状态下，即使它"走神"了——注意力从"分析财报毛利率"偏到了"分析行业竞争格局"——它仍然在 **RESEARCH.Allowed** 的集合内：分析、假设、验证。它不会突然开始写诗或给出人生建议，因为 FORBIDDEN 列表明确禁止了这些行为。

**漂移没有消失，但漂移的伤害被状态边界截断了。** 一个在 RESEARCH 里过度分析的模型，比一个从 RESEARCH 一路偏到 "我理解你的焦虑，投资确实很难..." 的模型要安全得多。

## 状态转移：谁决定切换

状态转移可以由两种方式触发：

### 方式 1：模型主动请求（推荐）

在状态 prompt 中告知模型当前状态的边界，以及如何请求切换：

```
## 如果用户的要求超出了当前状态的允许范围
不要强行在当前状态下处理。回复中声明：
"[STATE_SWITCH_REQUEST: DECISION] 用户要求给出投资建议，需要在 DECISION 状态下处理。"
```

解析这个标记，触发状态转移 + 注入新的状态 prompt。

### 方式 2：外部规则强制切

```python
# 基于规则的强制转移
def check_forced_transition(state: str, user_message: str) -> Optional[str]:
    """某些用户指令应强制触发状态切换"""
    triggers = {
        "DECISION": ["建议", "推荐", "选哪个", "怎么选", "给个方案"],
        "RESEARCH": ["分析一下", "看看数据", "对比", "趋势", "为什么"],
        "CLARIFY": ["什么意思", "没听懂", "再说一遍", "不清楚"],
    }
    for target_state, keywords in triggers.items():
        if target_state != state:
            if any(kw in user_message for kw in keywords):
                return target_state
    return None  # 不强制切换
```

## 漂移在这种设计下的表现

### 以前（无状态控制）

```
Turn 10: RESEARCH — 分析财报毛利率
Turn 12: 模型开始给投资建议（不知道自己在 RESEARCH 状态）
Turn 15: 模型开始安慰用户"市场波动是正常的"
Turn 18: 模型开始聊行为经济学
Turn 20: 用户问"我们刚才在说什么？"
```

### 现在（有状态控制）

```
Turn 10: RESEARCH — 分析财报毛利率
Turn 12: 模型继续分析（即使想给建议，FORBIDDEN 列表阻止了它）
Turn 14: 模型多角度交叉验证数据（在 Allowed 范围内发散）
Turn 16: 模型列出 5 个可能的解释（仍然是分析行为）
Turn 18: 用户说"给我建议" → 模型回复 "[STATE_SWITCH_REQUEST: DECISION]"
Turn 19: 切换到 DECISION → 注入 decision_prompt → 给建议
```

**模型在 Turn 12-16 之间确实漂移了**——它从"分析毛利率"偏到了"交叉验证数据"再偏到"列出 5 个解释"。但所有这些行为都在 RESEARCH.Allowed 集合内。用户看到的是一个"分析得很深入但有点啰嗦"的助手，而不是一个"完全忘记在干什么"的助手。

## 效果指标

| 指标 | v2.5 Compressor | v3 State Machine |
|------|----------------|------------------|
| 100轮指令遵循率 | ~60% | ~85% |
| 跑题严重程度 | 可能完全偏离 | **被限制在状态内** |
| 漂移恢复时间 | 手动 | 自动（<3轮，切状态或触发 DRIFT_RECOVERY） |
| 不该给出的建议 | 可能 | **被 FORBIDDEN 列表阻止** |
| 状态可追溯性 | 无 | 完整 checkpoint 链 |
| 断点续接 | 不支持 | 原生支持 |

> 注意：指令遵循率从 ~92%（旧版 README）调整为 ~85%。旧数字过于乐观——状态机在 100 轮的极限场景下，状态切换逻辑本身也会引入新的故障模式（如错误的状态判断导致注入错误的 prompt）。

## 已知局限

### 局限 1：状态判断本身可能出错

状态转移的判断器——无论是模型自判还是规则匹配——都可能犯错。模型可能在 RESEARCH 状态下强行给出建议（违反了 FORBIDDEN），或者规则匹配把一句反问误判为"要切换状态"。

**缓解**：双判——模型自判 + 规则兜底，不一致时以保守选择为准（RESEARCH 优先于 DECISION）。

### 局限 2：FORBIDDEN 不等于物理禁止

和 v2 的 `logit_bias` 不同，状态 prompt 中的 FORBIDDEN 是**文本约束**而非采样约束。模型仍然可能在 RESEARCH 状态下生成建议——只是我们告诉它"不要这样做"。对于指令遵循能力弱的模型，这个约束可能被忽视。

**缓解**：结合 v2 的 `stop_sequences`（检测到违禁输出时截断）+ 输出后处理过滤。

### 局限 3：状态爆炸

每增加一个状态，就需要定义其 ALLOWED/FORBIDDEN 集合和转移条件。当状态超过 10 个时，转移矩阵的维护成本急剧上升。

**缓解**：默认使用 5-7 个通用状态。只在确有必要时才添加领域特定状态。

### 局限 4：状态切换的延迟

从模型声明 `[STATE_SWITCH_REQUEST]` 到实际注入新的状态 prompt，需要至少一轮对话的延迟。这意味着在切换发生前，模型已经用"旧状态的视角"回复了一轮。

**缓解**：在关键边界（如用户明确说"给我建议"）使用规则强制切状态，绕过模型自判的延迟。

### 局限 5：v3 仍然需要 v2.5

当对话超过 100 轮时，即使有状态控制，每个状态内部的上下文也会膨胀。v3 的状态 prompt 注入不解决 token 预算问题——你仍然需要 v2.5 的压缩器来定期清理上下文。

**推荐组合**：v3（状态控制）+ v2.5（上下文压缩）+ v2（API 参数兜底）。
